# G1 decision record: comment-based progress reports

Scope and baseline: [task-genesis.md](task-genesis.md), [original plan](master_plan.md), `origin/master` at `23c4880`. This is a design contract, not a code change. The school currently does **not** want foundation children enrolled. Any school can opt classes of any level into narrative reporting later; never infer enrollment or reporting mode from the words "foundation" or from a grade level.

## What the worktree actually does

- [Student creation and promotion](../../../../packages/convex/functions/academic/studentEnrollment.ts) (`createStudent`, `promoteStudents`, `setStudentSubjectSelections`) are explicit enrollment operations. [FR-005](../../../issues/FR-005.md) distinguishes enrollment and guardian linking. Report-mode setup must not call these operations, create users, or provision portal credentials.
- [Term report settings](../../../../packages/convex/functions/academic/reportCardTermSettings.ts) (`saveTermReportCardSettingGroup`, `resolveEffectiveReportCardTermSettings`) already support named, non-overlapping sets of class IDs within a term, but only for shared next-term date and attendance settings. They are not report modes. [Schema](../../../../packages/convex/schema.ts) `reportCardTermSettingGroups` stores those lists. `schoolGroups` instead represents multi-branch ownership/defaults; it must not be reused for sets of classes.
- [Extras](../../../../packages/convex/functions/academic/reportCardExtras.ts) (`saveReportCardExtraBundle`, `setClassReportCardExtraBundles`, `saveStudentReportCardExtrasEntry`) and [model](../../../../packages/convex/functions/academic/reportCardExtrasModel.ts) support text and descriptive scale fields and school-scoped assignment. Class assignment is not term-scoped, and bundle definitions and scale labels can be replaced. Extras do not provide a report mode, required learning-area completion, a review state, or publication. Reuse the editor patterns, field validation and optional attendance/comment display, not live bundle references as the authoritative historical narrative report.
- [Graded builder](../../../../packages/convex/functions/academic/reportCards.ts) (`buildStudentReportCard`) returns an issued snapshot if present and otherwise builds a **live** report from assessment records, class subjects, extras and comments. `getStudentReportCard`/`getClassReportCards` are teacher/admin preview calls; `certifyStudentReportCard` requires `academic.report_cards.publish_final`, rechecks a reviewed key, rejects pending subjects and inserts `issuedReportCards`. [Schema](../../../../packages/convex/schema.ts) and [contract](../../../../packages/convex/functions/foundation/reportCardContract.ts) currently contain grade-specific fields. `saveStudentReportCardComments` locks edits after graded issuance; `saveStudentReportCardExtrasEntry` needs an equivalent mode-aware edit lock for new narrative data. Existing [report integration tests](../../../../packages/convex/functions/academic/__tests__/reportCards.integration.test.ts) exercise grading policy issuance and frozen media references.
- **Verified parent exposure:** [portal `getWorkspaceData`](../../../../packages/convex/functions/portal.ts) selects linked students through `getPortalStudentAccess`, then calls `tryBuildStudentReportCard`, which calls `buildStudentReportCard(...skipRoleCheck: true)` for both the selected card and history. This helper does **not** require `certifiedAt` or an `issuedReportCards` row. Thus a linked parent's portal can show live, uncertified graded results, extras and teacher comments today. The portal also derives pending-score and comment notifications from that live card. [Portal content](../../../../apps/portal/app/%28portal%29/components/portal-workspace/PortalWorkspaceContent.tsx) renders selected results and history. FR-009's checked results criterion describes current behavior; FR-008's published-portal criterion is still open. Do not claim graded cards already have a publish guard.
- [Shared `ReportCardSheet`](../../../../packages/shared/src/components/ReportCardSheet.tsx), [admin preview/batch print](../../../../apps/admin/app/assessments/report-cards/page.tsx), [teacher preview/batch print](../../../../apps/teacher/app/assessments/report-cards/page.tsx) and [portal view](../../../../apps/portal/app/%28portal%29/components/portal-workspace/PortalWorkspaceContent.tsx) expect numeric subject results. [Teacher workbench](../../../../apps/teacher/app/assessments/report-card-workbench/page.tsx), [admin review/certification](../../../../apps/admin/app/assessments/report-cards/components/CertifyReportCard.tsx), [admin bundle setup](../../../../apps/admin/app/assessments/setup/report-card-bundles/page.tsx) are the practical entry points. [Admin academic setup mockup](../../../../docs/mockups/admin/admin-academic-config.html), [class management](../../../../docs/mockups/admin/admin-class-management.html), [enrollment](../../../../docs/mockups/admin/admin-student-enrollment.html), and [teacher entry states](../../../../docs/mockups/teacher/teacher-exam-entry-states.html) establish navigation/context patterns, not a narrative screen specification.

## Decisions and trade-offs

1. Use **school + session + term + class** as the effective mode key, defaulting to `graded` when no explicit row exists. Admin can select any active classes in a named set and apply one choice in bulk. A set is a convenience for configuration, not a branch `schoolGroup`, student cohort, or a recurring rule. Persist a bounded per-class config row with unique logical key and optional term-scoped named-set ID; make the named set a separate record and keep class membership in indexed config rows rather than an unbounded `classIds` array. Validate all class/session/term IDs in the same school; reject duplicates and overlapping assignments. A newly created class or new term is graded until an admin explicitly chooses otherwise. A school-wide "disabled" state is the absence of narrative selections, not a tenant-level switch that changes every class. This is safer than school-level/grade-level toggles, which would silently capture future enrollments and rewrite old terms.
2. Narrative template has named **learning areas** (stable key, label, display order, required flag), a required teacher observation for each required area, optional descriptive scale with stable option keys and display labels, plus an overall teacher comment and optional head-teacher comment. No numeric field, mark-derived label, subject score, rank, total or average. One school-owned template version can be selected by multiple class-term configs; an admin edits a draft by creating a new version, never mutates the version used by an issued card. Optional attendance and branding may share existing collection/rendering behavior, but the publish payload copies their values and labels. Limit number and length of fields and comments; reject empty required observations at publish. Reusing extras unchanged would be quicker, but mutable global assignments and labels break history, and number/boolean fields admit score-like output. Keep a dedicated typed narrative template and snapshot instead.
3. Teacher with assigned-class/form-teacher access enters and edits per-student, per-area draft values only for the selected school, session, term and enrolled class; school admin may also edit. Admin reviews an assembled preview and explicitly publishes for one student. Reuse the reviewed-key pattern from `certifyStudentReportCard`: compare a revision/hash of all publishable narrative content and template version in the same mutation, reject stale previews, write an immutable issued snapshot, audit actor/time, and make repeated publishes idempotent. Admin-only publish uses existing `academic.report_cards.publish_final`; teacher entry uses the assigned-class/form-teacher rules already present in `reportCardExtras.ts`, not merely a client route check. After issue, reject changes to that period's narrative draft, template binding or mode; corrections require a separately specified supersession workflow, not in this slice. Graded certification must reject narrative class-terms; narrative publish must reject graded class-terms. No bulk auto-publish.
4. Use a **discriminated issued payload** with `kind: "graded" | "narrative"` for new reads; preserve legacy `issuedReportCards.report` graded rows without a discriminator as graded. Either extend `issuedReportCards` with an optional narrative-specific snapshot or use a separate narrative issuance table and compose a typed read model; prefer the separate table for minimal change to existing stored grade validators and certification. Enforce one issued kind per student/session/term across both tables in transactional mutations. Snapshot the school, class, student presentation, learning-area keys/labels/order, selected scale option keys/labels, observations, comments, attendance, template version, and school theme references/values needed for display. Apply existing safe media lookup rules; do not substitute a different student's image. Published content must be read from issuance, never reconstructed from editable drafts. A class-term with graded issuance cannot switch to narrative, and vice versa. An unissued class-term can switch after explicit warning; switching hides inactive-mode drafts, leaves drafts stored for authorized staff review, and does not expose them in the portal. Existing issued periods and their mode remain readable after later-term switches or template edits. This rejects midterm issuance rewrites without forbidding a school from choosing a different mode next term.
5. Build a **narrative-only parent publication gate in the Convex portal query**, not in React: for selected card, history, dashboard recent results and notifications, return only issued narrative snapshots; for a narrative class-term with no issue, return a neutral "report not ready" entry without scores, draft comments, scale values, or pending-score alerts. Determine historical mode from the immutable issued record first, then explicit class-term config, not the child's current class. Audit `preferredClassId: selectedStudent.classId` in `getWorkspaceData`, because a promoted student's current class is not reliable historical context. Apply gate before calling the live graded builder. Keep **graded** portal behavior unchanged for this feature, including its known uncertified exposure; broader graded publication lockdown is a separate security/product decision because it would change existing parent behavior. Do not leak narrative draft data through any generic results/history endpoint or notification.
6. Render one mode-specific report component behind a typed dispatcher for parent view, teacher/admin preview and one-student/class print. The narrative renderer must omit all grading semantics, including score columns and cumulative-backfill warnings; show school theme with accessible contrast, white printable paper and legible monochrome output. Batch print may include graded and narrative students only when each correct mode's payload is available; admin/teacher previews may print drafts visibly marked "Draft, not published". Parent print uses issued-only narrative snapshots. Preserve graded `ReportCardSheet` and existing batch behavior where possible.

## Acceptance and risks

[FR-023](../../../issues/FR-023.md) is the test checklist. Primary risks: existing parent live graded exposure; wrong historical class after promotion; mutable extras/templates; a route that returns drafts outside the new portal read model; large snapshot fields; and report mode versus class enrollment confusion. Require server tests for each. Non-goals: enrolling foundation students, a foundation-only policy, grade-level inference, changing graded publication semantics, AI-generated comments, automated publishing, superseding issued cards, and numeric proficiency scores. Existing [FR-006](../../../issues/FR-006.md), [FR-008](../../../issues/FR-008.md), [FR-009](../../../issues/FR-009.md), [FR-010](../../../issues/FR-010.md) stay in force for graded workflows.

No blocking product decision for the minimal contract above. FR-023 names this feature; the PRD retains FR-022 for admissions. The graded portal publication policy belongs to a separate agent's worktree. Coordinate changes to `packages/convex/functions/portal.ts` at integration and require both behaviors to hold.

## Reservation and entitlement contract

Existing internal quota reservation holds requested units transactionally against consumed+held; persisted operation name/key/amount rejects conflicting reuse. `status` is now in the returned result; `allowed` remains the historical acceptance flag for compatibility, **not permission to dispatch again**. A replayed reserved state also is not a dispatch lease. Commit charges actual <= held, releases remainder atomically, and identical actual retry is idempotent. Release is idempotent and consumes no customer allowance. Late commit after release rejects. Actual > estimate still rejects: this is precisely why no paid operation is enabled on top of it.

Legacy `allocateQuota` is additive internal maintenance, **not a purchased top-up receipt**: no receipt idempotency, plan version, cycle ID/expiry, grant audit or exception authority. New versioned entitlements must reference U5a immutable contract/rate IDs and dates. No catalog amount, invoice or mandate was used to infer an allowance. Stored reset cadence is descriptive; this packet does not implement a scheduler. Current 75/90/100 behavior is the existing base-limit contract, not grace support.

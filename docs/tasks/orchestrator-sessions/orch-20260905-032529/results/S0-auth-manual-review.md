## Blocking findings

### F1 — CRITICAL — A read/preview capability authorizes child-record writes

**Locations**

- `packages/convex/functions/academic/reportCards.ts:1079` — `saveStudentReportCardComments`
- `packages/convex/functions/academic/reportCardExtras.ts:621` — `saveStudentReportCardExtrasEntry`
- Generated by explicit overrides in `r1-capability-adoption.mjs`.

Both mutations require only `academic.report_cards.preview`. A managed caller holding a capability named and routed as read/preview can write class-teacher/head-teacher comments, attendance values, and report-card extra values. Teacher assignment/form-teacher checks narrow which children can be changed, but they do not make a preview permission a write permission. An admin with only preview can also write.

This contradicts the shared matrix statement that route/read gates do not authorize buttons or mutations and is the exact regex/misclassification hazard called out by the stabilization task.

**Required fix:** assign an operation-specific write capability. If `academic.assessments.enter` is the accepted contract, use it consistently; otherwise add explicit report-card comment/extras edit capabilities and migrate roles/routes. Keep `academic.report_cards.preview` on the read endpoints only. Add managed-caller tests proving preview-only denial and write-capability success for both admin and assigned/form teachers.

## Required warnings

### F2 — WARNING — Managed administrators cannot use any admin-leadership endpoint

**Locations:** `packages/convex/functions/academic/adminLeadership.ts:42,126,227,263,307,386,432,492`.

`listSchoolAdmins`, `promoteTeacherToAdmin`, `promoteSchoolAdmin`, `demoteAdminToTeacher`, `archiveSchoolAdmin`, `transferSchoolAdminLeadership`, and `restoreSchoolAdmin` call `getAuthenticatedSchoolMembership(ctx)` without `capability` or `membershipOnly`. `createSchoolAdmin` calls `getViewerContext({ legacyOperation: true })`. The managed-account helper intentionally fails closed in both cases. The new security test even proves only that these calls fail after management is enabled; there is no corresponding supported managed success path.

**Why it matters:** enabling permissions turns off core staff leadership administration even for a principal/proprietor with the expected capabilities.

**Required fix:** assign endpoint-specific contracts (`staff.list.view`, `staff.onboard`, `staff.permissions.manage`, and `staff.account.suspend` as appropriate), preserve the existing school/admin/leadership invariants, and test managed least-privilege allow/deny behavior for every operation.

### F3 — WARNING — The broad academic selector OR set reaches staff identities and student-derived data

**Locations**

- `packages/shared/src/workspace-capability-matrix.ts:3-9`
- `packages/convex/functions/academic/academicSetup.ts:1739` — `listClasses`
- `packages/convex/functions/academic/academicSetup.ts:2225` — `getClassSubjects`

`ACADEMIC_CONTEXT_CAPABILITIES` is an any-of list that includes finance, migration, enrollment, curriculum, report-card, assessment, and staff-assignment capabilities. Most uses return only school-scoped session/term/class/subject configuration and are acceptable. These two are broader:

- `listClasses` returns `formTeacherId`, `formTeacherName`, and a count derived from student rows.
- `getClassSubjects` returns assigned `teacherId` and `teacherName`.

Thus a managed admin holding only, for example, `finance.reports.view` or `system.migration.execute` can retrieve staff identity projections through a constant documented as containing no staff/child records. The existing tests exercise a full admin, not least privilege.

**Required fix:** split pure academic context DTOs from staff/roster projections, strip the staff fields for the broad selector contract, or require a narrower additional capability before returning them. Add a finance-only/migration-only projection test.

### F4 — WARNING — Institutional domain reads expose the DNS challenge to unrelated operational roles

**Location:** `packages/convex/functions/academic/institutionalEmail.ts:363-367` (`getSchoolEmailDomains`), via `emailAccess` at lines 20-30.

`emailAccess` allows any of `settings.domains.manage`, `staff.onboard`, or `enrollment.intakes.manage`. `getSchoolEmailDomains` then returns raw `schoolEmailDomains` documents, including `dnsTxtRecord` and provider/configuration state. Staff onboarding and enrollment operators need scoped mailbox/person workflows, not the domain-control challenge. `getEmailWorkbench` already demonstrates the safer projected domain DTO.

The verifier is internal, so the token alone is not a public state-transition bypass, but this is unnecessary disclosure of security/operational metadata.

**Required fix:** require `settings.domains.manage` (or the intentionally retained domain-request capability) for the raw challenge, and return only the safe domain projection to staff/student-address operators.

### F5 — WARNING — Managed teacher planning parity is not established and likely regresses

**Locations**

- All teacher planning/knowledge endpoints adopted `academic.curriculum.manage` through `r1-planning-adoption.mjs`.
- `requestKnowledgeMaterialUploadUrl` and `finalizeKnowledgeMaterialUpload` additionally require `assets.upload` at `lessonKnowledgeIngestion.ts:444-445,560-562`.
- `packages/convex/functions/academic/rbac.ts:21-137` has no least-privilege teacher factory role; the available `academic_director` role is an administrative bundle.
- No changed test creates a permission-managed teacher and proves assignment-scoped planning, source access, drafting, generation, or upload behavior.

Legacy untouched teachers retain role/assignment compatibility, but the moment a teacher is permission-managed, the old role checks no longer suffice. The teacher route itself now requires `academic.curriculum.manage`; upload requires a second capability that the route does not communicate. This may be intentional delegation, but no migration/default role or parity test proves it, and the current factory set offers no ordinary teacher role.

**Required fix:** explicitly define the managed teacher capability bundle/migration contract (including whether uploads are independently delegated), then test an assigned managed teacher, an unassigned teacher, a curriculum-only teacher, and a curriculum-plus-upload teacher across the planning endpoints. Do not resolve this by granting administrative curriculum powers implicitly unless that is the approved model.

### F6 — WARNING — Legacy storage claims are not bound to school or uploader provenance (**locally remediated: upload paths disabled; see `S0-storage.md`**)

**Locations**

- `packages/convex/functions/academic/assetStorageBoundary.ts:8-20`
- `schoolBranding.ts:134-177`
- `studentEnrollment.ts:145-170`
- `lessonKnowledgeIngestion.ts:557-562`

`assertStorageNotBoundToAsset` only proves that a storage ID is absent from four asset-pipeline tables. It does not prove which school/user generated the upload URL, and it does not claim/check school logos, student photos, or knowledge-material bindings. Upload URLs are returned without creating a school/caller-bound intent. Consequently possession of an unbound `_storage` ID can be used to attach an object in another tenant or reuse one object across legacy consumers; object IDs become bearer authority. The asset finalizer also cannot detect a prior logo/photo/knowledge claim.

The caller endpoints do correctly check their domain capability and school records, and the new helper correctly blocks already asset-bound/quarantined objects from legacy URL consumers. That is necessary but not a complete ownership boundary.

**Required fix:** create a school/caller/purpose-bound upload intent for legacy uploads and atomically claim it on save/finalize. Include all binding tables/purposes in a single uniqueness model (or equivalent indexed claims), and add cross-school/reuse/race tests. Continue denying asset-bound IDs in portal/report-card/branding/knowledge URL paths.

### F7 — WARNING — Group asset sharing requires hidden dual-branch membership

**Locations:** `packages/convex/functions/academic/assetWorkspace.ts:94-123`; `securityFixtures.ts:5-16`; `r1-test-fixtures.mjs`.

`listShareRecipients` and the grant path of `setBranchShare` call `requireCapability` in each recipient school. A source-branch asset-sharing operator therefore cannot share to another same-group branch unless the same identity is also an active member with `assets.library.view` there. Platform is terminally denied tenant capabilities, and group proprietorship by itself does not create a branch membership. The codemod changed the test actor to an all-capability operator seeded into both branches, so the test cannot reveal this practical denial.

The same-group, active-school, explicit-recipient and 50-share checks are otherwise sound, and revocation is correctly source-authorized.

**Required fix:** confirm the product contract. If owner-authorized metadata sharing is intended (as `U5d.md` states), validate recipient/group eligibility without requiring caller membership in the recipient. If recipient consent is required, model it explicitly rather than as an undocumented second membership. Test a normal source-only operator and a denied outsider.

### F8 — WARNING — All-capability fixtures mask operation-capability regressions

**Locations:** `packages/convex/functions/academic/__tests__/securityFixtures.ts:5-16`, plus codemod changes to asset, commercial/assets, email/AI, and migration/security tests.

`seedReviewedTenantOperator` assigns the entire `CAPABILITY_CATALOG`. This is appropriate for a small number of broad success fixtures, but the converted suites use it as the main proof that authorization works. It cannot detect F1, F3, F5, F7, or accidental extra-capability dependencies. There are no direct tests for either report-card write mutation, no managed-teacher planning parity test, and no action tests for the payment verification/reconciliation capability chain.

**Required fix:** retain a broad fixture only where irrelevant to the assertion; add a helper that accepts an explicit capability list and add operation-level allow/deny tests. Tests must separately prove school boundary, role/assignment scope, and exact capability.

## Optional suggestion

### F9 — SUGGESTION — `reconcilePendingOnlinePayments` accidentally requires two finance capabilities

`billing.ts:2277` authorizes the action with `finance.payments.record_manual`, then line 2283 invokes the public `listBillingPaymentAttempts`, which independently requires `finance.reports.view`. The standard bursar currently has both, so the broad fixture passes, but a custom least-privilege payment reconciler cannot run the action.

Use a school-bound internal query after the action's operation check, or explicitly document and test that reconciliation is an all-of operation. The rest of the billing action chains reviewed bind school/invoice/reference before internal mutation, and portal payment actions re-establish family/student invoice access.

## Decisions and trade-offs

1. **Vertical UI integration with small backend prerequisite changes, not UI-only wrappers.** Most M0–M8 modules have no app callers. Reusing them minimizes duplicate logic, but several contracts need correction before safe exposure. Each packet owns its domain and tests; internal functions remain internal unless a separately authorized public use case is implemented. A pretend settings screen that calls a partial or insecure API is not acceptable.
2. **One active-workspace contract, then bounded caller adoption.** Merely changing a header/local school ID leaves existing no-argument legacy APIs on the old branch. U1a establishes server-validated active context and an explicit compatibility contract; U1b installs it across actual shells/callers. Prefer explicit requested-school arguments and resolved server membership over mutating identity or legacy `users.schoolId`. This requires caller work but avoids cross-tab identity mutation and hidden global context. Retain legacy default-branch invocation for untouched clients; restrict switching to routes whose calls are scoped until adoption is complete, with an explicit explanation rather than wrong-school data.
3. **Reuse actual forms and route groups.** Keep billing configuration within `/billing`; teacher onboarding is on `/academic/teachers`, not a new imaginary onboarding URL. Reuse the migration workbench rather than a second importer. General assets remain separate from lesson knowledge. New routes below are proposals, never claimed as existing evidence.
4. **Serialized shared seams; independently reviewable domain PRs.** U1a owns auth contracts, U1b owns navigation/shell integration, U3a owns draft/guard framework, U3d owns themes. Domain owners submit navigation entries to U1b's established seam, not concurrent rewrites. Schema/generated API/package export changes have one writer at a time, coordinated by the parent. A packet's follow-on must not edit a predecessor's files concurrently.
5. **Honest gated features.** Provide reversible proposal/quarantine/read-only workflows without enabling mailbox providers, payment splits/mandates, scanner assertions or PDF promotion. Existing tests prove contracts only after rerun, not live provider readiness. No request for new planning approval; proceed with safe local build work and record genuine access blockers.

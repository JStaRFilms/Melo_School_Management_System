# Class result publication contract

Session `orch-20260928-083117`. Genesis specification, not deployment approval. Source of truth: `master_plan.md`; implementation must wait for the decisions at the end of this document. The score-entry window in `assessmentEditingPolicies` is about staff edits, not family access. Certification creates a per-student immutable copy. A separate, explicit class/session/term release governs family visibility. Existing terms start unreleased, including terms with issued copies.

## Proposed state and data contract

Use a dedicated `classResultPublications` table, keyed by `(schoolId, sessionId, termId, classId)` with a compound index including all four fields. A row represents only `released`, never a speculative draft. Fields: `schoolId`, `sessionId`, `termId`, `classId`, `releasedAt`, `releasedBy` (authenticated staff user), `releasedByMembershipId`/`personId` where available, `rosterVersion` or a stable readiness digest, `eligibleCount`, `certifiedCount`, `excludedCount`, `createdAt`. A separate immutable audit event records actor, tuple, counts, confirmation and outcome using the existing audit helper; keep the audit's safe summary free of scores. No row means withheld. If a school later needs revocation, design it as an audited state transition, not deletion of certification. Add this table to tenant purge, branch-split and seed/cleanup inventories after reviewing those manifests. On large deployments stage the new index for backfill before querying it.

The effective family-read predicate is: authenticated active portal membership with access to this non-archived student in this school, valid session and term in this school, a verified historical enrollment for the exact class in that session/term, exactly one released publication for that tuple, and exactly one certified snapshot matching that tuple and student. Check the released row before reading/returning report details. Return the snapshot, with only existing safe image-URL hydration; never reconstruct live scores or borrow current policy. Release must not change staff preview semantics. Snapshot lookup for a single term must not assume a student's current class: a transfer or class change can leave an earlier class in a different school/session. The existing `getIssuedReport` lookup without class uses `.unique()` on `(student,session,term)` and cannot represent two same-term class histories; resolve that collision before shipping multi-class history.

API changes:

- `functions/academic/resultPublication:getClassReadiness({sessionId,termId,classId})` returns a bounded/paginated, staff-authorized roster with certification status and explicit reasons, counts, and stable review token. No draft marks in the readiness response. Authorized staff can still use existing previews to fix a row.
- `functions/academic/resultPublication:releaseClassResults({sessionId,termId,classId,reviewedKey,confirmation})` is an atomic Convex mutation. Derive school and actor from authentication, require `academic.report_cards.publish_final` plus school-admin authorization policy resolved below. Check class/session/term school and term.sessionId; reject archived or inconsistent tuple, empty roster, missing/invalid policy snapshots, duplicate issued snapshots and any unapproved omission. Recompute readiness inside the mutation and compare review key to stop a stale confirmation. Write release and audit together; retry on the same released tuple returns the original release metadata without another audit or widening scope. Different review token or tuple cannot republish or overwrite it. Concurrent release attempts serialize by the same indexed tuple read/write; test uniqueness under simultaneous calls.
- `functions/portal:getWorkspaceData` retains `selectedReportCard: report | null`. Add explicit selected-result state (`released`, `withheld`, `no_eligible_record`) if UI needs to distinguish these without inspecting results. History contains only eligible released reports or separately typed score-free availability notices, never fake zero summaries. Avoid an authenticated API claiming that an unpublished certified copy exists.

Do not use the editing window, `finalizationEnabled`, `finalizeAt`, or dates as release state. `saveAssessmentEditingPolicy` currently forces `finalizationEnabled: false`; do not piggyback on it.

## Roster, historical access and readiness

The roster used by readiness and the release mutation must be the same server-side definition. Candidate evidence: eligible school students for the class/session, `studentPromotions`, class/session subject selections, assessment records, and issued cards. Current batch roster (`getStudentsForClassReportCardBatch`) considers current students only when `session.isActive`, but adds old selections/records; `isStudentEnrolledInClassForSession` falls back to `student.classId` if no promotion and rejects archived student rows. This can misattribute a past term to a newly assigned current class, or omit a transferred source student whose row was archived. Do not use `preferredClassId: student.classId` as proof of historical membership. Establish a persisted enrollment/term roster or verified session/class evidence before release. A promotion into the session is evidence for its class; old term class records or selections are evidence only after tenant and consistency checks; unknown historical membership blocks release rather than guessing. A transfer creates distinct source/destination student rows. Release stays owned by the branch that produced each snapshot; never copy scores or release status to the destination branch. The canonical login may select its non-archived source row after transfer (see `portalIdentity.ts` and `transfers.integration.test.ts`), so a source report can be read only under source membership, source school's release, and matching source issued copy. An archived destination after reversal must not expose its report unless a separately approved access policy exists.

Recommended default readiness: freeze an explicit eligible roster for the tuple, require one immutable matching certified snapshot for every eligible student, and block release otherwise. A student with partial marks, incomplete cumulative term, no grading-policy snapshot, no subjects, missing historic enrollment evidence, or duplicate report is a blocker. Do not quietly drop withdrawn, graduated, transferred, archived or missing-account students from the denominator just to make a class green. Provide an explicit audited exclusion decision per student with reason and actor if product policy permits; excluded students never receive that tuple's report even if a snapshot exists. Capture roster/digest and exclusions at release. Define what happens when a late admission, promotion correction, transfer, or certification occurs after release: readers must never pick up an unreviewed student solely because a new issued row appears. Prefer frozen eligible student IDs stored as child rows keyed by release and student (not an unbounded array on the publication row), and require a separate audited amendment workflow if late additions are supported. If amendment is not in scope, show staff a blocked/manual-remediation state rather than auto-publish. Keep transactions bounded; a large class needs a reviewed preflight/freeze design that cannot release a subset accidentally.

## Admin and family interaction requirements

Design a class/session/term readiness panel in Admin, not Teacher, with eligible, certified, missing, excluded counts and named blockers; link each missing row to its existing report-card review. Certification UI (`apps/admin/.../CertifyReportCard.tsx`) currently says issued copies are used by Portal; change it to distinguish certification and class release. Only an authorized releaser sees a confirmation naming school, class, session, term, release count and irreversibility policy. Disable submit until readiness succeeds and require the fresh review token. On success show release timestamp and actor; retries show the original event. Family dashboard and direct `/results` and `/report-cards` links show a neutral "Results for this term have not been published" message when withheld, and a distinct "No report card is available for this enrollment" message for missing eligibility. Suppress subject tables, averages, comment alerts, history metrics and report/print controls for withheld results. Published older terms can remain browsable without becoming the current-term summary. Design must preserve white print paper and semantic grade/status colours; UI team runs `node scripts/audit-theme-colors.mjs` on touched school-facing files.

## Rollout, rollback and checks

1. Resolve the policy questions below and capture representative historical, transfer and current-class fixture data. Tell schools before rollout: previously visible draft results, even already certified cards, will disappear from family screens until staff explicitly releases each class/term/session. No automatic backfill or timed release.
2. Deploy schema and server-side **default-deny family gate together**, before exposing any release controls. A schema-only deploy with the old portal handler still leaks drafts. Ensure old client bundles cannot query any ungated family endpoint. Keep staff certification/preview usable. Check portal response in a production-like test school before release UI is enabled.
3. Deploy readiness/release endpoints and Admin UI after the gate. Let schools certify historical records where the issued policy exists. Historical records lacking an issued grading-policy snapshot currently fail certification (`gradingPolicy.source === historical_missing` in `gradingPolicy.integration.test.ts`); do not regrade them with today's bands silently. Block release and provide a reviewed historical import/reconciliation procedure if approved.
4. Pilot one school/class with authorized school approval; compare roster and issued counts, check parent/student responses, transfer-source selection and audit. Broaden only after checks and explicit deployment authorization.

Rollback must never restore the old portal query, which reads drafts. Stop new releases by disabling the write control and mutation via a server-side setting while retaining the default-deny read gate and already released snapshots. An emergency hide-all-results switch may force the read gate closed without deleting records. Roll forward with corrected server/client code. If revocation is requested, log and scope it explicitly; do not delete audit or snapshots. No merge, migration or deploy without the user's approval.

Verification: Convex `convex-test`/Vitest edge-runtime tests for draft (including partial) and certified-but-unreleased privacy across selected card, history, notifications, direct URL, old client args and multi-school family membership; release only issued copies despite later score/comment/policy changes; authorized and denied staff; tenant and session/term/class mismatch; stale readiness; missing/duplicate snapshots; empty/partial roster and all exclusion statuses; retry and concurrent release audit exactly once; historical promotion, withdrawal, graduation, source transfer, reversal and archival; newly admitted student after release; bounded history with newer withheld terms; image and print path. Add portal UI tests for selected-term withheld state, old released history, child/term switch and stale data, desktop/mobile results and printable report. Run typecheck, lint, focused tests and theme audit for touched UI, plus independent authorization review.

Acceptance means no family API returns scores, grades, totals, subject/pending counts, comments, draft-derived hints or report URLs for a withheld tuple. Released access yields only the correct immutable certified copy for an explicitly eligible student in the same school/class/session/term. Each release is explicit, authorized, scoped, readiness-checked, audited, idempotent and safe under retry/concurrency. Historical data receives no implicit release. A failed or rolled-back rollout never reopens draft access.

## Owner decisions, 2026-09-28

- Exam officers with the existing `academic.report_cards.publish_final` capability may release a class as well as certify. Continue to verify school membership and the exact class/session/term tenant boundary server-side.
- Permit only school admins to enter explicit, audited per-student exclusions with a reason. Do not silently omit uncertain, withdrawn, transferred, or uncertified students. The readiness view must show exclusions before release; exam officers may release an already reviewed roster, but cannot author exclusions.
- Freeze each release's eligible student list. Later additions or corrections never become visible automatically; a separate reviewed amendment workflow is out of scope for this PR.
- Older records lacking a certifiable grading-policy snapshot remain hidden. Surface the blocker to staff and defer a historical reconciliation/import workflow.
- For unresolved within-term multi-class history, fail closed instead of guessing a class or choosing an arbitrary snapshot. Only show a score-free withheld message for the selected term; history lists released terms only. These last two are conservative implementation defaults, not approval for publishing ambiguous records.

## Original decision register

1. Who may release a class? Existing `academic.report_cards.publish_final` is also used to certify and is granted to `exam_officer`; should release require that capability plus `assertAdminForSchool`, a distinct `academic.report_cards.release_class` capability, or an additional school-lead approval? Do not infer this from the certification permission.
2. What is the authoritative historical eligible roster when promotions, selections and records disagree, and how are active students with no marks, withdrawn/graduated students, archived transferred source students and mid-term transfers handled? Which exclusions may an admin approve, with what reason/evidence? Without a signed policy the safe state is unreleased.
3. Can a released class later admit a missed student, amend exclusions, revoke visibility or re-release? The proposed frozen roster disallows automatic additions. Define amendment/revocation authority and audit before supporting them.
4. How should older records with `historical_missing` grading policy become certifiable without rewriting historical marks or applying current grade bands? This blocks some historic releases today.
5. Can a student have two valid classes and issued reports in the same term? Current three-key `.unique()` forbids this. Specify family selection and release behavior for genuine within-term moves.
6. Should unpublished terms appear in family history as score-free placeholders, or only a selected-term withheld message? The latter avoids revealing the existence of an assessment and avoids fake zeroes.

- Structured updates preserve an omitted middle. Send `middleName: null` to clear it on student, parent, and teacher edit contracts.
- Legacy full-name-only people return their full display name with unknown parts as null. Do not split `name` in the frontend. Use full-name mode until the operator deliberately supplies first and last parts.
- Full-name-only renames clear stale structured fields. Do not send blank first/last fields alongside a legacy full-name edit.
- Teachers, leadership/admin provisioning, canonical person creation, group projections, admissions adult contacts, and migration paths now carry middle names. School-local edits do not rename other schools' projections.

Reviewed imports can retain this full-name-only mode. `migrationAutosave.patchStagedRecord` accepts optional `name` and nullable `middleName` in `parsedDataPatch`, with the existing record ID and expected row revision checks. First/last remain required for structured mode, not inferred from the full name.
- Admissions draft and immutable detail reads project the two-word-first rule without rewriting legacy rows or snapshots. New admissions contact inputs retain required `fullName` for compatibility and accept optional first/middle/last plus address mode. Conversion preserves those parts instead of reparsing full names.

### Atomic enrollment contract

Required inputs remain `admissionNumber: string`, `classId`, and `gender`. Send either structured `firstName`/`lastName` with optional `middleName`, or a legacy `name`. Existing optional demographics, house, guardian text, address, photo metadata, numbering review, manual-number confirmation, request-key, and draft-closure inputs remain supported.

New choices:

```ts
parentGuardian?:

      kind: "existing";

      relationship?: string | null;

  | {
      kind: "new";

    };
addressMode?: "residential" | "different";

```

`parentGuardian` and legacy `parentLink` are mutually exclusive. Legacy `parentLink` still accepts required first/last/email plus optional middle/phone/relationship/family label/primary flag. An exact-email match reuses the existing contact; incoming identity fields are ignored, not used to rename it. Preserve the existing duplicate-review step and send `confirmDuplicateLink: true` after review. Stored-ID choices reject students, archived users, and foreign-school IDs. After success, query the returned student ID. Do not infer success or account state from the cleared form or a prior request's sidebar. Account provisioning remains a separate explicit action, never part of linking an existing parent.

### Student profile and class confirmation

`getStudentProfile({ studentId })` returns `userId`, stored `email`, `name`/`displayName`, nullable `firstName`/`middleName`/`lastName`, effective `classId`/`className`, and nullable `activeSessionId`. It also returns demographics/house, retained guardian text, `photoUrl`/`photoFileName`/`photoContentType`, enrollment/graduation fields, and:

```ts
address: string | null;                 // effective value
storedAddress: string | null;           // retained student copy
addressMode: "residential" | "different" | null;
addressSource: "residential" | "different" | "legacy" | "none";
emergencyContactMode: "primary" | "override" | null;
emergencyContact: {
  source: "primary" | "override" | "legacy" | "none";
  parentUserId: Id<"users"> | null;
  name: string | null;
  phone: string | null;
  email: string | null;
};
portalState: PortalState;
```

A null raw mode means legacy/unspecified, not permission to overwrite it with a frontend default. Identity-only edits should omit unchanged class, modes, address, guardian text, and photo inputs. A legacy emergency override remains legacy until deliberately changed. `getStudentAttestationData.student` now also includes nullable middle name.

`updateStudent` retains its optional identity/demographic/numbering inputs. Class effects require:

```ts
{
  studentId,
  classId: targetClassId,
  confirmClassAssignment: true,
  expectedClassId: reviewedProfile.classId,
  expectedSessionId: reviewedProfile.activeSessionId,
}
```

Only send this after the conditional changed/conflicting-class dialog. Confirmation requires one valid active session and a valid target class. Stale expected class/session causes a reload/review error and no writes. Without confirmation, supplied class values do not reconcile selections, retire promotions, or alter the base class. Historical selections stay intact.

`setStudentSubjectSelections({ schoolId?, studentId, classId, sessionId, subjectIds })` authorizes the admin or assigned teacher, validates tenant/class/session/archive state, and checks effective membership for that selected session. Empty `subjectIds` clears that student/class/session only. All/toggle use the same API; they do not require an identity/class reassignment first.

### Contact, household, and address contracts

All public contact operations retain enrollment capability and branch-admin checks.

- `searchParentContacts({ search, paginationOpts: { numItems, cursor } })` accepts 1 to 50 items and at most 100 search characters. Returns standard `page`/`isDone`/`continueCursor`; each item has `userId`, `displayName`, nullable name parts/phone, email, role, `portalState`, and `households`. Search filters each bounded tenant page, so continue pagination even if a filtered page is empty and `isDone` is false.
- `getParentEmailReview({ email })` returns normalized `email` and up to three exact local matches with `userId`, name, email, phone, role, archive flag, and `families`. It intentionally exposes duplicate/archived/student cases for review rather than approving them for linking.
- Both household summaries expose ID/label, residential address, the selected contact's address mode/override/effective address/source, nullable actual primary contact with ID/name/phone/email, and student/parent counts. When the student has no household, existing-contact linking reuses the oldest matching local household as before; show that reviewed household rather than assuming the selected contact is primary.
- `upsertStudentFamilyLink({ studentId, parentUserId, ...linkInputs })` supports explicit stored-ID linking. The legacy new-contact first/middle/last/email path remains supported. It returns `{ familyId, parentUserId, familyMemberId, createdHousehold }`. Existing identities are not patched. Existing member address overrides survive relinking, including exact-email matches with new-form address defaults.
- `getStudentFamilyProfile({ studentId })` returns nullable `family` with ID/label/residential address/counts, `parents`, and linked student summaries. Each parent has family-member ID, user ID, name parts, role, relationship, primary flag, email/phone, address mode/override/effective value/source, and `portalState`.
- `updateStudentFamilyParentContact({ familyMemberId, name?, firstName?, middleName?, lastName?, email?, phone?, relationship?, isPrimaryContact?, confirmPrimaryChange?, confirmDuplicateEmail?, addressMode?, addressOverride? })` is the explicit edit path. Phone/relationship/address override can be null; middle can be null. Staff identities remain link-only here and use their staff management path. Returns `{ familyId, parentUserId, familyMemberId }`.
- `updateHousehold({ familyId, name?, residentialAddress?: string | null, confirmed: true })` edits the label/common residential address explicitly. Returns null. Common-address changes affect inheriting contacts and students; different-address overrides and stored student copies stay intact.
- `deleteUnusedParent({ parentUserId, confirmed: true })` returns null only after proving the school-local parent is unused. Archived students, retained references, canonical linkage/history, or an exceeded review bound block deletion. It never deletes auth accounts, canonical persons, or other-school records.
- `removeStudentFamilyLink` remains an unlink operation, not identity deletion.

Use the common relationship choices for convenience and persist actual custom text. Do not convert an old custom relationship into a generic Other value. Same-address mode is `residential`; only `different` requires a nonempty override. New households can initialize their common address from admission address. Linking another child never replaces a reused household's common address. Set student mode to `residential` deliberately to inherit; otherwise preserve its captured/legacy address.

### Login suffix and portal contracts

Null selects the school-namespaced `.local` default. Configured domains must be eligible verified registry entries with unique ownership; existing active-group sharing rules apply. Stale versions are rejected and the change is audited. This applies only to new student identities, including imports and conversions.

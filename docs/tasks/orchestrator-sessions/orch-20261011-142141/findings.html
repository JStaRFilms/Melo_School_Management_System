What the code explains

Grouped by your original report numbers. These are source-code findings, not an inspection of your live school records. Implementation is waiting for the choices below.

1, 2

Parent names, reuse, and removal

Current behaviorLinking an existing parent can overwrite their name. The household label is stored separately, and the portal header can read another name source. Unlink removes a relationship, not the parent account.

Proposed fixChoose an existing parent without retyping. Linking will not edit identity. Keep explicit Edit, make household labels clearly separate and editable, and add the cleanup policy you choose.

3, 12

Wrong active class after promotion

Current behaviorThe roster uses session promotions; the profile reads the base class. Saving a name also reconciles subjects against that base class, without needing the confirmation checkbox.

Proposed fixShow the effective active-session class. Keep confirmation for deliberate reassignment. Identity saves must leave promotion and subjects untouched.

4, 9

Two admission flows and blank profile names

Current behaviorGuardian text is stored on the student; linked parents are separate records. The roster form collects first/last names but sends only a combined name. Names longer than two words can then have blank structured fields.

Proposed fixOne admission flow, student details entered once, optional family linking, and explicit name parts saved. Preserve old guardian text rather than silently converting or deleting it.

6, 9

Optional middle names for everybody

Current behaviorImports and applicants already have some middle-name support, but school identities do not. Some displays prefer first/last and drop the middle from a stored full name. Teacher renames can also leave stale name parts.

Proposed fixFirst / middle / last across students, parents, teachers, staff, admins, admissions, imports, drafts, reports, and certificates. Keep middle optional. Do not guess how old full names should split.

7, 10

Provisioned versus not provisioned

Current behaviorThe success view exists only in component memory. Reopening loses it. An ordinary student profile save can also overwrite the provisioned auth linkage.

Proposed fixPersist and load actual linked-account state. Separate Provision, Provisioning, Provisioned, and Reset password. Reopening must not imply a second provisioning is needed. Never persist temporary passwords just to rebuild the screen.

5

Connection warning and page movement

Current behaviorThe badge measures the Convex connection, not general internet access. Draft status can stay stale after reconnect. Rendering it above the page content changes the layout.

Proposed fixOne fixed header status location. Distinguish server reconnecting, sign-in needed, and unsaved draft recovery. Clear stale state without discarding edits.

8

Student login identifiers

Current behaviorAn admission number such as ADM/001 becomes adm001@students.local. It is not an email inbox. The ID has no school namespace, so equal admission numbers in different schools can collide during provisioning.

Proposed fixKeep working logins stable. New logins need collision-safe identifiers. Choose whether to show a clear login ID or build school + admission-number sign-in.

10

Results from older sessions

Current behaviorThe backend already permits authorized older published reports. The visible history requests eight records, with a backend maximum of twelve and no continuation. Older reports can therefore disappear from the list.

Proposed fixAdd usable history navigation beyond that limit. Keep the child's ownership and publication checks. Existing issued snapshots remain as published; corrected names flow into live and newly issued documents.

11

Resend notifications

Current behaviorThe school repo already has a durable Resend outbox and idempotent delivery pattern. Whisper uses configurable sender settings. Neither source proves the live verified domain. The school contact fallback mentions hey@jstarstudios.com.

Proposed fixUse the configured, verified JStar sender with school-labelled messages. Notify only deliverable addresses, never @students.local. Keep email delivery separate from account success, and limit duplicate notices to one per recipient/school in five minutes.

The recommended admission flow

Student identity + class→Optional family contact→One admission save

Family contact offers “Choose existing” or “Create new”. A different emergency contact stays optional. Portal provisioning remains an explicit action with its own actual status.

# Backend handoff: session scoring

The backend now uses a guarded, in-place regrade. There is no 100-record limit. The guard covers the entire scan, the confirmation window, every regrade batch, and failed batches. Session score entry, report previews and prints, certification, reviewed imports, and other assessment readers reject requests while the guard is active. Other sessions remain available.

Admin API sequence, all under `functions/academic/sessionScoring`:

1. `getSessionScoringPolicy({ sessionId })` gives the effective policy and version.
2. `startSessionScoringScan({ sessionId, policy, expectedVersion, expectedPolicy })` locks the session and schedules a full scan. It rejects another running or ready job for that session.
3. Poll `previewSessionScoringChange({ sessionId, policy })` or `getSessionScoringJob({ sessionId })`. `scanning` and `failed_scanning` counts are partial. `ready` has the complete number of records, complete invalid-record count and up to ten field-level examples. Only `ready` with `canApply: true` permits confirmation. `invalid` keeps the lock so its count cannot go stale through normal writes. Cancel that scan to unlock score entry, correct the rows, and start a fresh scan.
4. `applySessionScoringChange({ sessionId, policy, expectedVersion, expectedPolicy, confirmRegrade: true })` starts the regrade. Its response means **started**, not completed. Poll the job for `complete`. Only the last transaction publishes the new policy version and audit event, with the exact number of updated records. The job holds progress and a frozen grading-band snapshot between batches. Issued report payloads remain unchanged; issued-print queries warn when the completed version exceeds the report's certified version.
5. A failed batch rolls back and records `failed_scanning` or `failed_regrading` plus `failureReason`. `resumeSessionScoringJob({ sessionId })` restarts from the committed cursor and halves the batch size after a recorded failure, down to one row. A failed regrade stays locked and cannot be cancelled. `cancelSessionScoringScan({ sessionId })` releases a scan or ready confirmation window, not an in-progress regrade.

Old sessions with assessment rows use the recorded exam raw maximum and available imported policy snapshot when resolving legacy weights rather than borrowing a subsequently changed school input mode. For rows without an imported policy snapshot, the legacy contract supplies CA 20/20/20 and exam contribution 40. If a session has no records, its original school input mode cannot be reconstructed; the current effective school setting is used. If historical rows in a session contain conflicting snapshots, the first row only supplies a bounded compatibility starter for the editor; it does not establish a trustworthy session-wide history. Existing rows remain readable and edits use each row's recorded maximum. The full-session scan reports mixed legacy evidence and lets an admin apply a new explicit policy after checking for scores above the new maxima. This does not reconstruct an original session-wide policy. The regrade removes import policy snapshots from recalculated rows because they would otherwise falsely describe the newly derived results; immutable issued reports keep their own original payload.

Tests cover a 101-row regrade, an invalid row count across multiple batches with class and subject references, mixed raw40/raw60 legacy reads and explicit reconciliation, a failure after the first committed batch followed by resume, cancellation and resume after group governance changes, guarded reads and writes, tenant isolation, stale policy versions, legacy mode fallback, and the portal's warning for an unchanged issued report. Existing admin UI is unchanged. It must call the scan API before apply and show that apply has started rather than succeeded until the job reaches `complete`.

# Demo-school schema coverage gate

The offline test `packages/convex/schemaCoverage.test.ts` runs in the normal `pnpm --filter @school/convex test` suite. It reads the exported Convex validators from `schema.ts` and compares every application table, typed ID path, `_storage` path, `v.any()` boundary and `by_school` index with `schemaCoverageRegistry.json`. Arrays use `[]`, records use `{key}` or `{value}`, and nested objects use dots. Optionality and ID targets are part of the comparison. A new table, path, changed target/optionality, removed path, changed validator shape, or changed `by_school` index fails the test. The `shape` fingerprint is calculated from the whole exported document validator, so scalar additions also trigger review. A field that is neither a typed ID nor `v.any()` is outside this test; inspect string identifiers and storage URLs manually. Better Auth component tables live outside the application schema and are **not** covered by this gate.

This is a classification gate, not permission to run a reset. The public demo seed now refuses populated schools before changing Better Auth credentials or sessions. Its legacy internal 85-table deletion entry point also refuses demo-school. Empty-school seeding requires a development gate, a matching server `CONVEX_CLOUD_URL` and separately configured `DEMO_SEED_EXPECTED_CLOUD_URL`, and explicit inspected null school ID plus the exact `demo-school` slug. The read-only inspector does not authorize deletion. The reviewed populated-school execution path is separate from this first-run seed. Deletion stops at `ready_to_seed`; the separate FINISH action reseeds only the bound reviewed operation.

## Current inventory

The baseline now covers 180 application tables. `demoResetOperations` is a deployment-level `operator-global` reservation with an exact target school ID; it is outside `TENANT_SCHOOL_TABLES` and tenant storage scans. Its `storageCandidateIds[]`, `storageAcknowledgedIds[]` and ordered `retainedStorageIds[]` paths are `inventory-not-owner`, not independent file claims. Preparation seals exactly 37 distinct original run IDs, checks school logo and all 36 student photos by admission number, and requires every retained ID in the reviewed candidates. Reservation rechecks the succeeded run, live references, blobs and foreign claims in one transaction. Row deletion leaves the operation record intact. During storage cleanup, ACK requires a retained blob to exist without other claims; it never deletes it. Other candidates still require missing blobs and no claims. The final ACK checks all 37 retained blobs and every deleted candidate again before `auth_pending`. The public `executeDemoReset` Node action deletes only nonretained reviewed candidates. The internal auth phase rechecks the operation seal, development cloud URL, missing reviewed school, retained blob existence and deleted blob absence, and absence of all three credentials from application users, persons, memberships, platform admins and admissions guardians. `authAcknowledgedIds[]` stores a sequential prefix of the recorded IDs; only three acknowledgments move the operation to `ready_to_seed`. Better Auth remains separate: the Node action finds each email, compares its Better Auth ID to the recorded ID, reconciles sequentially, then acknowledges. It returns only `ready_to_seed` and the operation ID. It does not start a seed. The internal `startDemoSeedRunInternal` accepts an optional `resetOperationId`: only the exact reviewed operation can reuse its ordered 37 retained files after storage and auth ACK. START checks the configured server issuer, development target, old-school absence, all 37 blobs without foreign claims, and competing active operations in the insertion transaction. It records `newSchoolId` and `newRunId` as it advances to `seeding`; a matching `seeding` or `complete` replay returns that run ID without new rows. The public `finishDemoReset` Node action accepts the exact reviewed target, inventory hash and stored full phrase. Before START or any seeding or complete replay, it reads each Better Auth user with accounts and requires the recorded ID and exactly one credential account linked to that ID, without writes. It uses the retained files to START or replay. It resumes each bounded population mutation from its committed cursor and leaves retryable failures running. The final mutation verifies the succeeded run, exact IDs and 36 students, three classes, 36 invoices and 756 assessments before changing the operation to `complete`; subsequent calls revalidate and return the same result. A failed run is not repaired. Preflight checks the path against the registry but does not use ledger candidates as retained-owner claims or deletion authority. Every active operation from `prepared` through `seeding` blocks another preflight for the `demo-school` slug. Cancelled or completed history does not. Resume an interrupted reset with the same reviewed operation and its stored target, hash and phrase; do not prepare a replacement. The previous 179-table baseline covered: 156 direct `schoolId` tables with `by_school`, two direct tables without that index, 15 indirectly linked tables, and six shared/global tables. It records 694 typed ID or opaque paths, including 20 `_storage` paths. The indexed purge manifest has 154 entries; `branchSettingOverrides` and `roleTemplates` use separate indexed cleanup in `tenantPurge.ts`. The older `DEMO_SCHOOL_TABLES` seed list has 85 entries; it is deliberately checked for valid indexed membership, **not** assumed complete. There are 15 tables in the tenant storage inventory. These are three different contracts, not interchangeable deletion lists.

Two direct-school exceptions still need deliberate cleanup work. The read-only preflight now uses a global `.take(1001)` on each table. It treats an empty scan as proof of no rows in that table and blocks when the scan reaches 1001, even if none of those rows names the demo school. It does not use this scan for deletion:

- `admissionNumberClaims.schoolId` has `by_school_number` but no `by_school`. Add a suitable index and bounded, verified cleanup after reviewing claims and retries.
- `usageBranchPoolAllocations.schoolId` has no `by_school`; the existing group-pool orphan cleanup only removes allocations when the whole group becomes orphaned. Allocations for a retained group may survive. Add a safe indexed school-specific handling path after reviewing retained group ownership.

`studentTransfers`, `assetBranchShares`, and `migrationState` contain cross-school links. Deleting a received share or transfer can alter another school's records. `persons`, `schoolGroups`, `admissionsGuardians`, `platformAdmins` and Better Auth identities can be shared. A school ID reachable through one of these does not confer ownership of the row or account. `subscriptionInvoiceStudents`, membership children and usage children depend on their parents; delete children before parents, and verify residual references. `schools` is the root and its logo is a storage claim. `v.any()` paths are recorded as opaque boundaries: validator introspection cannot reveal IDs hidden inside them.

The read-only populated-school preflight checks each storage table in a separate bounded transaction using the tenant-purge candidate and retained-owner collectors. It includes the school logo, rejects retained file claims, unsupported storage paths with target rows, and any failed or overflowing inventory. The action uses separate transactions, so its result is an observation, not an atomic lock or permission to delete. It requires at most one school, a complete inventory of indexed direct rows at 1000 per table, no unindexed-scan overflow, no cross-school links, and exactly three matching credential owners. A seeded single-school cohort can now return `ready: true`; the public seed still refuses a populated school.

The current `storageIdsOnRow` helper in `seed.ts`, also used by `tenantPurge.ts`, does not traverse `importWorkspaces.sourceFiles[].storageId` or read `pdfCompressionCandidates.sourceStorageId`. Those paths are marked `unsupported-block-reset` in the registry. This is a known gap, not a safe exception. The helper also cannot prove that a file is unclaimed outside its listed tables or Better Auth components. The reviewed reset checks the storage ledger and retained-owner claims before deleting a blob; do not delete a file on the strength of a single tenant reference. The registry's `legacy-extractor` label describes the current field-name extraction, not a guarantee of exclusive ownership.

## When adding or changing a feature

1. Run `pnpm --filter @school/convex exec vitest run schemaCoverage.test.ts`. Read every new/changed path in the failure output and inspect the actual schema validators, including optional unions, arrays, records, `v.any()`, string-encoded IDs and storage references. Never regenerate the registry wholesale to silence the diff.
2. Add the new table to `schemaCoverageRegistry.json` with an ownership category, a specific `reason`, the complete `references` array, the actual `bySchool` value and the current `shape` fingerprint. For a changed table, inspect its schema diff first, then obtain the value from `schemaReferenceInventory(schema)["tableName"].shape` in a temporary local Vitest inspection test and copy it into the registry. Remove that temporary test afterward. If a field changed, update its exact path, target and optionality. Give each `_storage` path a `storage` disposition; add an `unsupported-block-reset` entry if extraction or exclusive ownership is not established. `inventory-not-owner` is reserved for the three `demoResetOperations` storage arrays and does not authorize file deletion. The check rejects missing/obsolete storage paths. Review both inbound and outbound links and whether the owner can be shared across schools.
3. A direct `schoolId` table needs a valid `by_school` index and an entry in `TENANT_SCHOOL_TABLES` in `tenantPurgeManifest.ts`, unless an explicit indexed special case is implemented and reviewed in `tenantPurge.ts`. `admissionNumberClaims` and `usageBranchPoolAllocations` require bounded read-only scans and remain cleanup blockers when rows are present. New direct-unindexed tables require a reviewed exception in the registry and must block reset until a bounded path exists. Add child-before-parent handling and residual verification for indirect rows. Avoid deleting cross-school rows merely because they mention the target school.
4. Review `DEMO_SCHOOL_TABLES` in `seed.ts` separately. Its omission of a table must be intentional; the gate only proves its entries are valid. Review `TENANT_STORAGE_TABLES` in `tenantPurgeAction.ts`, `storageIdsOnRow`, the storage-claim boundary, school logo handling, and files referenced by retained rows. Add fixture tests for shared ownership, missing files, interrupted retries, and the new path. Do not add an unsafe delete route just to make an inventory green.
5. Rerun `pnpm --filter @school/convex test`, `pnpm --filter @school/convex typecheck` and lint. The test includes an in-memory new-table/nested-file-path fixture which must fail classification, then verifies the real schema passes. Review the registry diff with the schema diff and update this guide when ownership or reset order changes.

## Populated reset and separate reseeding

Slice 1 provides an operator-gated, non-destructive `prepareDemoReset` action and a separate cancellation action. Preparation requires the populated preflight, exact development cloud URL, a bounded ID/digest inventory and an atomic `prepared` reservation. A second preparation cannot replace that record. The full operation hash binds the exact school ID, deployment, row digests, person/auth IDs, storage candidates and ordered retained IDs; the fresh typed phrase also includes the full hash. The gated `executeDemoReset` action compares the stored fresh phrase, exact hash, school and deployment before authorizing the prepared operation. Internal deletion batches recheck row digests, indirect and reverse links; storage and auth phases check their own recorded boundaries. Cancellation only marks a prepared operation `cancelled`. Execution stops at `ready_to_seed`; call FINISH separately to resume or complete the bound seed. A prepared record without the exact phrase is not permission to delete.

The older legacy reset is not the reviewed execute path. The legacy reset omits direct-school tables, canonical persons and memberships, and some storage references. An existing Better Auth credential account without a demo school also blocks empty-school seeding until its ownership is reviewed. The execute action stops after deletion and auth reconciliation; only the separate FINISH action populates the bound operation. Do not use the judge profile or tenant purge to work around this restriction. `e2e/global-setup.js` retains the first-run path on an empty target. For a ready, blocker-free existing cohort, it requires an interactive non-CI terminal, prepares an operation, displays the bound target and counts, and requires the exact fresh phrase before execute and finish. Cancellation marks the prepared operation cancelled. Interrupted resets require explicit same-operation resume in a new interactive terminal; an unknown or blocked cohort does not seed or reset. See [the operator runbook](DemoSchoolOperatorRunbook.md) for exact target gates and setup steps.

## Operator boundary

A reset requires exact development deployment proof for the CLI and each app URL, a bounded inventory of school rows, indirect references, shared identities and file claims, a reviewed backup reference, and an interactive typed confirmation for populated demo data. Treat shared or unknown links as hard blockers, even with confirmation. Only after the preflight and reset implementation have independent security review should an operator run a reset, then verify empty tables, special references, storage and authentication effects. None of these steps are performed by the schema gate. No production or production-copy target is authorized by this guide.
